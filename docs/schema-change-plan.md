# FAQ·문의 처리 상태 스키마 변경안

사용자가 공유 DB 적용을 보류했다. SQL만 준비했고 실행하지 않았다.
FAQ·문의 상태 기능 코드는 적용 여부를 읽어 미적용 시 저장을 차단한다.
공지 기능은 기존 테이블만 사용한다. 아래 절차는 향후 별도 승인 후 운영자가 수행한다.

## 적용 순서

운영자가 백업/복원 지점을 확보하고 다른 팀원에게 DDL 적용 시점을 공유한 뒤
`python/migrations/001_faq.sql`, `002_inquiry_status.sql` 순으로 한 번씩 실행한다.
MySQL DDL은 자동 커밋되며 실행 중 메타데이터 잠금이 발생할 수 있다.
스크립트는 기존 구조와 충돌하면 실패하도록 작성했고 자동 실행하지 않는다.

## FAQ

`faq`에 ID, 작성 관리자, 질문, 답변, 생성·수정·삭제 시각만 추가한다.
기존 데이터 이관은 없으며 빈 테이블로 시작한다. 삭제 시각이 NULL인 FAQ만 로그인 사용자에게 공개한다.
카테고리·임의 정렬·공개 토글은 현재 요구에 필요하지 않아 추가하지 않는다.
기본 정렬은 생성일 내림차순과 ID이며, 초안/비공개가 필요하면 별도 정책을 먼저 정한다.
관리자 ID FK와 같은 문자셋을 사용하고 기존 테이블은 변경하지 않는다.

## 문의 상태 (확정)

`question.processing_status`는 RECEIVED(접수), IN_REVIEW(확인 중),
NEEDS_INFO(추가 확인 필요), RESOLVED(처리 완료) 중 하나다.
관리자는 모든 상태 간 수동 변경할 수 있고 답변 등록은 상태를 자동 변경하지 않는다.
기존 문의와 기존 사용자 API가 새로 작성하는 문의는 DEFAULT RECEIVED로 초기화된다.
답변 유무 `answered`와는 독립적이다. 마지막 변경 관리자와 시각을 함께 저장한다.
첨부자료 제출, 추가 상태 이력 테이블은 포함하지 않는다.

## 되돌리기

먼저 백업하고 신규 API 사용을 중단한 뒤 `python/migrations/rollback.sql`을 운영자가 실행한다.
기존 공지·문의·답변 행은 삭제하지 않지만 FAQ와 추가 상태 메타데이터는 없어지므로
운영 데이터가 생긴 뒤에는 백업 없이 실행하지 않는다. 적용을 되돌리기보다 신규 기능을 중단하고
스키마를 유지하는 방법도 가능하다. 전체 DB 초기화나 기존 테이블 삭제는 수행하지 않는다.
